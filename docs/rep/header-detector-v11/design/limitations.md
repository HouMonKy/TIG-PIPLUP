# 已知缺陷、适用范围与未解决问题

## 1. 已知残余失败模式（E3-B τ=0.4 下，pooled 18,798 行）

| 失败模式 | 案例 | 残余量化 | 归属 |
|---|---|---|---|
| 值样正文首词（族级混合） | Mac `-[ObjC selector]` 深过剥与其正确剥离同组合同族 | 26 行 over（Mac 族 val over ~12%，τ=0.4 放行） | 结构上局部不可分，E3 残余 |
| 同族低 val over 误删 | BGL `idop` 值样正文 | 7 行（val over 0.7% 低于任何合理 τ） | 阈值本质限制 |
| 空白级 over（GT 怪癖） | 挑战集 39 行前导空格 | 零内容损失（content_over 已分离） | GT 侧，E5 前可修 |
| 无括号/无分隔符格式 | HealthApp `a|b|c|body`（管道单 span） | 0% acc，各方法一致 | E2 范畴确认无解（span 无助于无分隔符格式） |
| 异构节点字段 | HPC `node-246` vs `Interconnect-0N03` vs `full` | 0.229 acc（E0 起一致） | 位置类型不可分 |
| 跨源误路由 | 误配来源 + 精确结构碰撞 | dsware 570/1707 accept 行 over（正确路由下 0） | 来源名=安全边界（D10），非规则缺陷 |

## 2. 覆盖率损失（τ=0.4 的代价）

- 覆盖 0.884→0.714（-17pp）；正确剥离损失 11.75%，93% 集中在
  Mac/messages/OpenStack/oam 四个验证集高危族——这些族的 val
  over 本就 5–25%，属门控设计内的合理代价而非过拟合。
- 需要更高覆盖时用 τ=0.2（覆盖 0.771 / over 0.91%），或按业务
  模块单独放宽 τ（规则按源编译，天然支持 per-source 工作点）。

## 3. 适用范围（已验证边界）

- **验证域**：14 Loghub 公开数据集 + 8 个源自真实业务格式模板
  （format_chaos）的合成压力集 + 1 个独立种子挑战集；23 源；
  每源 800–2000 行；Python 3.13.5 单线程。
- **未验证域**（推断/待 E5）：生产规模日志量与源数（>736 源仅做过
  路由平坦性探针，非真实数据）；非拉丁字符日志；PIPLUP 端到端
  集成；规则随日志格式漂移的重编译节奏；多行日志（堆栈跟踪）——
  本阶段全部按单行处理。
- **已知敏感行为**：来源名错误时精确结构碰撞可剥离正文（D10）；
  classify 记忆化为 64K 条有界缓存（极高频不同 token 流会退化为
  无缓存性能，不会错误）。

## 4. 未解决问题（转 E5 或后续）

1. **E5 组合验证**（计划 §10）：E1 规则框架 + E2-D 分词 + E3-B
   门控 + E4-P3 运行时的完整组合已在 E4 内隐式组合并逐行等价
   （E4 规则即三者编译产物），但 E5 还需：PIPLUP 端到端集成实验、
   端到端额外开销 <5% 目标、E1 式 per-source 方法选择是否在
   span 签名上重建后仍有增量（E4 用了"全源统一 E2-D"的保守等价）。
2. Mac 深过剥与 BGL idop 类残余（§1）——若 E5 需要更低 over，
   需比 (签名,组合) 更细的规则键或 per-source τ，均未实验。
3. 挑战集 GT 前导空格修正（D12）。
4. 规则治理流程（版本化、审计、漂移检测）未设计。
5. 历史差异声明：E1 结果基于修复前 M3 参照系与 22 数据集
   （无挑战集）；跨实验精确对比以 E2 报告 §1.3 与 E4 报告 §3
   的对账表为准。

## 5. 依赖与环境

- 纯 Python 标准库（无第三方依赖）；实测 Python 3.13.5 /
  Apple Silicon / macOS（ru_maxrss 口径为字节）。
- 性能数字为单线程 median-of-5、GC 关闭、预热 300 行口径；
  不同硬件需重测（E4 报告 §4）。
