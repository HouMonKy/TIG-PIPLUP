# PIPLUP 算法端到端性能对比实验报告

> 数据集：单个模块数据 58 场景 / 9,452,830 行

---

## 结论摘要

**做了什么**：对两种日志模板解析算法（Drain3、PIPLUP）在相同数据集上使用各自正式生产管线进行端到端对比测试，指标覆盖性能、CPU、内存三个维度。

**最终结论**：PIPLUP 端到端吞吐为 Drain3 的 2.87 倍（冷启动）和 5.15 倍（缓存启动），CPU 时间减少 65.2%（冷启动）/ 80.5%（缓存启动）。内存增量 PIPLUP 略高于 Drain3（+27.3% / +23.7%），整体处于同一量级。Drain3 存在 8,819 行跳过（占总行数 0.093%），PIPLUP 无跳过。

**PIPLUP 的关键性能优化**：数据遍历方法——去掉 pandas DataFrame + `iterrows()` 遍历，改为原生 Python list 索引遍历。改动最小、风险最低、收益最高，在保持算法行为完全一致（输出逐行比对 100% 一致）的前提下，较优化前实现冷启动吞吐提升 38.0%，缓存启动提升 47.0%。研发过程中还评估了另外 3 项优化（set查找、提前终止、单次遍历），实测均为负贡献，已否决。

## 一、实验设计

### 1.1 算法配置

| 算法 | 说明 | 测试方式 |
|---|---|---|
| Drain3 | 固定深度树 + FilePersistence 缓存 | `parse_logs_dem` |
| PIPLUP | 前缀树 + 两级CRC32缓存，原生 list 索引遍历（数据遍历优化已合入） | `parse_logs_piplup_adapter` |

### 1.2 测试口径说明

两种方案使用相同输入数据，在各自正式生产管线下进行端到端测试。由于管线后处理逻辑不同，该结果用于比较实际生产管线吞吐，不代表解析内核的纯算法性能差异：

| | Drain3 | PIPLUP |
|---|---|---|
| 调用方式 | `parse_logs_dem` | `parse_logs_piplup_adapter` |
| 每行额外处理 | 格式解析 + **参数提取** + 结果构造 | 格式解析 + 结果构造 |
| log_repository.add() | **已排除**（NoOp替换） | **已排除**（NoOp替换） |
| 管线额外开销 | **高**（参数提取为主要耗时） | **中**（无参数提取） |

### 1.3 运行模式

| 模式 | Drain3 | PIPLUP |
|---|---|---|
| 冷启动 | 不加载 .bin 文件 | 每次运行前删除 .pkl 缓存，从空树开始 |
| 缓存启动 | 加载已有 .bin 缓存 + warmup 5000 条 | 先运行一遍建立缓存，再正式计时 |

### 1.4 指标定义

| 类别 | 指标 | 采集方式 |
|---|---|---|
| 性能 | 总吞吐量(lines/s) | 58场景总行数 / 58场景累计解析耗时 |
| | 总解析时间(s) | time.perf_counter() |
| CPU | 平均CPU利用率(%) | psutil 50ms 采样加权平均 |
| | CPU峰值(%) | psutil 采样 max |
| | CPU时间(s) | 进程 cpu_times() 增量 (user+system) |
| 内存 | 峰值RSS(MB) | psutil 采样 max |
| | 稳态RSS(MB) | 运行结束+gc后采集 |
| | 内存增量(MB) | peak_rss - baseline_rss |
| | MB/百万行 | 内存增量 / (nlines/1e6)，每百万行额外内存开销 |
| 跳过 | skip_count | Drain3 未被模板匹配器处理的行数 |

### 1.5 数据集

58 个场景，共 9,452,830 行（Messages 模块）。两种算法使用完全相同的数据集。

### 1.6 测试环境

| 项目 | 配置 |
|---|---|
| Python | 3.11 |
| 内存隔离 | 每种算法独立子进程运行，确保内存完全释放 |
| 采样间隔 | psutil 50ms 采样线程 |

## 三、结果分析

### 3.1 性能：PIPLUP 在冷启动和缓存启动均显著领先

PIPLUP 冷启动吞吐 4,363 lines/s，为 Drain3（1,521 lines/s）的 2.87 倍；缓存启动 7,649 lines/s，为 Drain3（1,487 lines/s）的 5.15 倍。

领先来源有两部分：

- **数据遍历方法优化**：去掉 DataFrame/`iterrows()` 后改为原生 list 索引遍历，消除每行约 150us 的 Series 创建开销，较优化前实现冷启动 +38.0%、缓存启动 +47.0%（见第四节）。
- **算法结构优势**：前缀树 + 两级 CRC32 缓存。缓存启动下 L1+L2 有效命中绝大多数行可跳过树搜索路径，PIPLUP 缓存启动较冷启动再提升 75.3%；而 Drain3 的 FilePersistence 缓存无收益（-2.2%），其缓存仅持久化聚类状态、不能减少每行的匹配计算。

### 3.2 CPU：PIPLUP CPU 时间大幅减少

PIPLUP 冷启动 CPU 时间 2,155s，较 Drain3 的 6,188s 减少 65.2%；缓存启动 1,231s，较 6,330s 减少 80.5%。两种算法平均 CPU 利用率均接近 100%，说明对比在相同算力供给下进行，CPU 时间差异即真实计算量差异。

### 3.3 内存：PIPLUP 内存增量略高，处于同一量级

PIPLUP 内存增量较 Drain3 高 27.3%（冷启动）/ 23.7%（缓存启动），主因是 PIPLUP 前缀树结构本身占用更大。但两者处于同一量级（671-862MB），且均已排除仓库写入开销；MB/百万行分别为 71.6-91.2，差距约 20MB/百万行，工程上可接受。数据遍历优化移除 DataFrame 后未引入额外内存开销，实测内存增量较优化前实现略有下降（-4.3% / -1.3%）。

## 四、数据遍历方法优化详细说明

### 改动

将 `pd.DataFrame` + `iterrows()` 遍历改为原生 `range` + `list[idx]` 索引，并同步修改 post-loop 阶段的 DataFrame 访问（`self.df_log.at[index, 'Content']` → `log_list[index]`）：

```python
# 优化前
self.df_log = pd.DataFrame(log_list, columns=['Content'])
self.df_log.insert(0, 'LineId', range(1, len(log_list) + 1))
for idx, line in self.df_log.iterrows():
    content = line['Content']
    logID = line['LineId']

# 优化后
self.df_log = None
total_lines = len(log_list)
for idx in range(total_lines):
    content = log_list[idx]
    logID = idx + 1
```

### 为什么有效

`iterrows()` 每次迭代创建一个 pandas Series 对象，包含类型推断、索引构建等开销（约 150us/行）。9.45M 行 x 150us 仅遍历框架开销约 1,400s。原生 `list[idx]` 是 C 级 O(1) 操作，无 Python 层对象创建。

### 实测收益（相对优化前实现）

| 指标 | 冷启动 | 缓存启动 |
|---|---|---|
| 吞吐 | 3,161→4,363 lines/s（**+38.0%**） | 5,204→7,649 lines/s（**+47.0%**） |
| CPU时间 | 2,980s→2,155s（**-27.6%**） | 1,813s→1,231s（**-32.1%**） |
| 内存增量 | 901MB→862MB（**-4.3%**） | 841MB→830MB（**-1.3%**） |

### 安全性

优化仅改变遍历方式，不改变遍历顺序和内容，不触及聚类/匹配/迁移逻辑。原版实现不依赖任何 DataFrame 特有语义：

- pandas 自动类型转换：Content 列已全是 str，无隐式转换
- DataFrame index 对齐：LineId 是顺序整数，无自定义索引语义
- Series 向量化操作：循环内只做逐行读取，无 .str/.apply 等向量操作
- in-place 修改：循环内从不通过 Series 修改内容

已通过 3 场景逐行比对验证：EventTemplate 一致率 100%（0 mismatch），EventId 一致率 100%。算法行为完全一致。优化同时移除了 pandas 依赖，无额外空间开销（DataFrame 对象约 50-100MB 被释放）。

## 五、已否决的优化项

在数据遍历方法优化之外，研发过程中还评估了 3 项纯算法优化，通过 leave-one-out 消融实验（8 变体 x 2 模式 x 58 场景）逐项测量边际贡献，结果均为负贡献，已否决。

### 5.1 总览

| 优化项 | 思路 | 理论预期 | 消融实测（冷/缓存） | 判定 |
|---|---|---|---|---|
| set查找 | `token in list` → `token in set()` | O(KxN)→O(K+N) | -3.2%/-2.9% | 否决 |
| 提前终止 | seqDist 不可超越时提前退出 | 减少无效比较 | -1.7%/-1.7% | 否决 |
| 单次遍历 | tree_restructure 逐个 index+pop → 一次遍历收集 | O(N^2)→O(N) | -1.9%/-0.2% | 否决 |

### 5.2 共性根因：小 N 下常数因子主导

三项优化有一个共同的失败模式：**理论复杂度更优，但 PIPLUP 场景下 N 很小，常数因子开销超过理论收益**。

| 优化 | 理论改进 | 实际 N | 为何负贡献 |
|---|---|---|---|
| set查找 | O(KxN)→O(K+N) | token序列 5~30 个元素 | set 构建开销 > K 次短序列线性扫描 |
| 提前终止 | 提前退出省比较 | 候选簇中位数 < 5 | bookkeeping 开销 > 少数触发的节省 |
| 单次遍历 | O(N^2)→O(N) | 迁移数 1~3 个 | N^2 与 N 差异可忽略，代码路径更长 |

数据遍历方法优化之所以成功，是因为它消除的是与 N 无关的固定开销（每行 150us 的 Series 创建），对所有数据规模都有效。

## 六、结论

### 算法对比

| 维度 | Drain3正式管线 | PIPLUP正式管线 |
|---|---|---|
| 冷启动端到端吞吐 | 1,521 lines/s | **4,363 lines/s**（2.87 倍） |
| 缓存启动端到端吞吐 | 1,487 lines/s | **7,649 lines/s**（5.15 倍） |
| 冷启动CPU时间 | 6,188 s | 2,155 s（-65.2%） |
| 缓存启动CPU时间 | 6,330 s | 1,231 s（-80.5%） |
| 冷启动内存增量 | 677 MB | 862 MB |
| 缓存启动内存增量 | 671 MB | 830 MB |
| 跳过数 | 8,819 | 0 |
| 输出一致性 | — | 与优化前实现逐行比对 100% 一致 |

### 决策依据

| 维度 | 评估 |
|---|---|
| 端到端吞吐（vs Drain3） | 冷启动 +186.7%（2.87 倍），缓存启动 +414.5%（5.15 倍） |
| CPU（vs Drain3） | 冷启动 CPU 时间 -65.2%，缓存启动 -80.5% |

| 风险 | 最低（已移除 pandas 依赖，无额外空间开销） |

**最终选择**：采用数据遍历优化（原生 list 索引遍历）后的 PIPLUP 作为最终版本；不采用 set查找/提前终止/单次遍历。
