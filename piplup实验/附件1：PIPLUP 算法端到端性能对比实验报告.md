# PIPLUP 算法端到端性能对比实验报告

> 数据集：单个模块数据 58 场景 / 9,452,830 行

---

## 结论摘要

**做了什么**：对三种日志模板解析算法（Drain3、PIPLUP原版、PIPLUP优化版）在相同数据集上使用各自正式生产管线进行端到端对比测试，指标覆盖性能、CPU、内存三个维度。

**最终结论**：PIPLUP优化版通过消除 DataFrame/iterrows 遍历开销，在保持算法行为完全一致的前提下，冷启动吞吐提升 38.0%，缓存启动提升 47.0%。在当前正式生产管线下，PIPLUP优化版端到端吞吐为 Drain3 的 2.87 倍（冷启动）和 5.15 倍（缓存启动）。

**优化版是什么**：去掉 pandas DataFrame + iterrows() 遍历，改为原生 Python list 索引遍历。改动最小、风险最低、收益最高。研发过程中还评估了另外 3 项优化（set查找、提前终止、单次遍历），实测均为负贡献，已否决。

## 一、实验设计

### 1.1 算法配置

| 算法 | 说明 | 测试方式 |
|---|---|---|
| Drain3 | 固定深度树 + FilePersistence 缓存 |`parse_logs_dem` |
| PIPLUP原版 | 前缀树 + 两级CRC32缓存，无优化 |`parse_logs_piplup_adapter`|
| PIPLUP优化版 | 移除原版DataFrame | 正式管线 `parse_logs_piplup_adapter`|

### 1.2 测试口径说明

三种方案使用相同输入数据，在各自正式生产管线下进行端到端测试。由于管线后处理逻辑不同，该结果用于比较实际生产管线吞吐，不代表解析内核的纯算法性能差异：

| | Drain3 | PIPLUP |
|---|---|---|
| 调用方式 | `parse_logs_dem` | `parse_logs_piplup_adapter` |
| 每行额外处理 | 格式解析 + **参数提取** + 结果构造 | 格式解析 + 结果构造 |
| log_repository.add() | **已排除**（NoOp替换） | **已排除**（NoOp替换） |
| 管线额外开销 | **高**（参数提取为主要耗时） | **中**（无参数提取） |

### 1.3 运行模式

| 模式 | Drain3 | PIPLUP |
|---|---|---|
| 冷启动 |不加载 .bin 文件 | 每次运行前删除 .pkl 缓存，从空树开始 |
| 缓存启动 |加载已有 .bin 缓存 + warmup 5000 条 | 先运行一遍建立缓存，再正式计时 |

### 1.4 指标定义

| 类别 | 指标 | 采集方式 |
|---|---|---|
| 性能 | 总吞吐量(lines/s) | 58场景总行数 / 58场景累计解析耗时 |
| | 总解析时间(s) | time.perf_counter() |
| CPU | 平均CPU利用率(%) | psutil 50ms 采样加权平均 |
| | CPU峰值(%) | psutil 采样 max |
| | CPU时间(s) | 进程 cpu_times() 增量 (user+system) |
| 内存 | 峰值RSS(MB) | psutil 采样 max |
| | 稳态RSS(MB) | 运行结束+gc后采集 |
| | 内存增量(MB) | peak_rss - baseline_rss |
| | MB/百万行 | 内存增量 / (nlines/1e6)，每百万行额外内存开销 |
| 跳过 | skip_count | Drain3 未被模板匹配器处理的行数 |

### 1.5 数据集

58 个场景，共 9,452,830 行（Messages 模块）。三种算法使用完全相同的数据集。

### 1.6 测试环境

| 项目 | 配置 |
|---|---|
| Python | 3.11 |
| 内存隔离 | 每种算法独立子进程运行，确保内存完全释放 |
| 采样间隔 | psutil 50ms 采样线程 |
| 并行 | 管线与核心测试并行运行，各自独立子进程 |

## 三、结果分析

### 3.1 性能：优化版在冷启动和缓存启动均显著提升

PIPLUP优化版冷启动吞吐 4,363 lines/s，较原版 3,161 lines/s 提升 38.0%。提升来源是 DataFrame/iterrows 移除后遍历开销降低。两者走相同管线 `parse_logs_piplup_adapter`，口径一致，可直接归因到 DataFrame 移除。

缓存启动下优化版提升 47.0%（5,204→7,649），与核心算法测试中缓存启动 +45.9% 的提升一致，说明管线固定开销未显著稀释 DataFrame 移除的组件优化收益。冷启动提升 38.0% 高于核心级的 28.5%，原因是管线路径中 DataFrame 移除不仅消除了解析内核的遍历开销，还减少了管线层对象构造的开销。

### 3.2 CPU：优化版减少CPU时间（冷启动）

PIPLUP优化版冷启动 CPU 时间从 2,980s 降至 2,155s（-27.6%），缓存启动从 1,813s 降至 1,231s（-32.1%）。缓存路径 CPU 收益更为显著，与吞吐提升趋势一致。

### 3.3 内存：管线开销占内存增量主要部分

三种算法内存增量在同一量级（677-901MB），即使排除了仓库写入开销。PIPLUP 内存增量略高于 Drain3（+27%），主因是 PIPLUP 前缀树结构本身占用更大。优化版 vs 原版内存增量改善有限（-4.3%），因为管线对象累积占内存增量的绝大部分。

## 四、DataFrame移除优化详细说明

### 改动

将 `pd.DataFrame` + `iterrows()` 遍历改为原生 `range` + `list[idx]` 索引：

```python
# 原版
self.df_log = pd.DataFrame(log_list, columns=['Content'])
self.df_log.insert(0, 'LineId', range(1, len(log_list) + 1))
for idx, line in self.df_log.iterrows():
    content = line['Content']
    logID = line['LineId']

# 优化后
total_lines = len(log_list)
for idx in range(total_lines):
    content = log_list[idx]
    logID = idx + 1
```

### 为什么有效

`iterrows()` 每次迭代创建一个 pandas Series 对象，包含类型推断、索引构建等开销（约 150us/行）。9.45M 行 x 150us 仅遍历框架开销约 1,400s。原生 `list[idx]` 是 C 级 O(1) 操作，无 Python 层对象创建。

### 安全性

优化版仅改变遍历方式，不改变遍历顺序和内容，不触及聚类/匹配/迁移逻辑。已通过 3 场景逐行比对验证：EventTemplate 一致率 100%（0 mismatch），EventId 一致率 100%。算法行为完全一致。

## 五、已否决的优化项

在 DataFrame移除之外，研发过程中还评估了 3 项纯算法优化，通过 leave-one-out 消融实验（8 变体 x 2 模式 x 58 场景）逐项测量边际贡献，结果均为负贡献，已否决。

### 5.1 总览

| 优化项 | 思路 | 理论预期 | 消融实测（冷/缓存） | 判定 |
|---|---|---|---|---|
| set查找 | `token in list` → `token in set()` | O(KxN)→O(K+N) | -3.2%/-2.9% | 否决 |
| 提前终止 | seqDist 不可超越时提前退出 | 减少无效比较 | -1.7%/-1.7% | 否决 |
| 单次遍历 | tree_restructure 逐个 index+pop → 一次遍历收集 | O(N^2)→O(N) | -1.9%/-0.2% | 否决 |

### 5.2 共性根因：小 N 下常数因子主导

三项优化有一个共同的失败模式：**理论复杂度更优，但 PIPLUP 场景下 N 很小，常数因子开销超过理论收益**。

| 优化 | 理论改进 | 实际 N | 为何负贡献 |
|---|---|---|---|
| set查找 | O(KxN)→O(K+N) | token序列 5~30 个元素 | set 构建开销 > K 次短序列线性扫描 |
| 提前终止 | 提前退出省比较 | 候选簇中位数 < 5 | bookkeeping 开销 > 少数触发的节省 |
| 单次遍历 | O(N^2)→O(N) | 迁移数 1~3 个 | N^2 与 N 差异可忽略，代码路径更长 |

DataFrame移除之所以成功，是因为它消除的是与 N 无关的固定开销（每行 150us 的 Series 创建），对所有数据规模都有效。
